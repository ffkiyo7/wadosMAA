## 一、核心排序逻辑

整套项目刚完成 Phase 3 生产切线（`~/.wados-maa` + 守护进程 + Bark + iOS App），Phase 4 等 11-29 窗口终验。下一阶段如果直接堆新页面和新功能，会撞上三个现实约束：

1. **数据底座仍是 Discord 文本遗留**：日常战报 `report.json` 存的是 Discord Embed 原文，`ios/Core/RunReport.swift` 还在靠字符串匹配捞结果；同时 `runs/` 14 天自动清理、`runs/index.jsonl` 满 600 行裁至 500 行且不含把数与掉落明细。**统计墙和 Heads-up 必须先有结构化数据与永久账本，晚一天落地就多丢一天历史。**
2. **交互模型仍是 Discord 卡片遗留**：`maa_action.py` 里的手动派发与抄作业仍围绕选关卡/token/过期哨兵建模，而 iOS `StartRunSheet` 即使关掉「刷理智」也被迫选关、缺快捷预设与空档排队。**必须先把派发模型迁到 API 意图，再谈托管流与前端改版。**
3. **iOS 改动成本高（个人账号 7 天签名 + 真机安装）**：新页面与 UX 大改应压到**你拿着 iOS App 逐页走查对齐之后**一次性落地，避免前端返工两遍。
4. **已确认的高痛点前置并行**：「抄作业导航通用化」不依赖 F0/F1 且你已在 11-24 确认要做，直接放到 M1 与数据底座并行，活动期尽早止血。

主线顺序：**全量 Review → 数据底座（F0）∥ 抄作业导航通用化 → 交互模型与统一派发（F1）→ 托管流 ∥ Heads-up 后端 → 用户 UI 对齐门禁 → iOS/Mac UI 一次落地 → 深层重构与历史清理**。

## 四、已拍板的 5 项决策（2026-11-25）
