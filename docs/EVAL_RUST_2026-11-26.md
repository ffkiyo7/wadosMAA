# 后端换 Rust 评估（2026-11-26，北京时间）

> 范围：`maa-remote/` 后端整体或部分改用 Rust 的代价与收益，以及「fork maa-cli 再加回现有实现」的思路。基于 `dev` @ `6a163e2`，代码与 `main` 一致。
> 依据：读代码、git 历史、`maa-remote/docs/incidents/`、11-25 全量 Review、本机线上守护进程的实际占用、maa-cli 上游仓库（`MaaAssistantArknights/maa-cli` @ `v0.7.8`）。全程只读，没装 Rust、没开游戏、没改代码。

## 一句话结论

**留在 Python。** Rust 常说的优势（性能、内存、并发安全、类型系统）在本项目大多落不到实处，真正能体现的三条（不依赖解释器、成熟的 HTTP/TLS 库、重构时编译器兜底）都能在 Python 里用小成本补上。整体迁移要 5～8 周，期间 ROADMAP 停摆，不划算。

「直接链接 MaaCore 拿结构化回调」确实有价值，但它和换不换语言无关：给 maa-cli 打一个小补丁就能拿到，后端仍是 Python，可以在 M1a 结构化战报 v2 时考虑。

`maa-remote/docs/incidents/` 31 份，全部是游戏界面、弹窗、代理、上游资源、窗口、测试隔离这类问题，没有一份和语言有关。08-08 的 SIGSEGV 是 MaaTouch 崩溃，不在我们的代码里。

## 3. Rust 在本项目的优势

### 开发维护

| 优势 | 能否体现 | 依据 | Python 内的替代 |
|---|---|---|---|
| 编译期类型检查、枚举必须穷尽 | 部分 | 状态枚举（`status`、`failure`、锁持有者）、回执 `code`、跨端 JSON 字段确实适合；但历史 fix 里没有这一类 | 契约模块开 pyright strict，用 `Literal` / `TypedDict`；Swift 和 Python 共用 golden fixture |
| 大重构时编译器兜底 | 能 | M2 拆 `maa_action`、M5 拆 `maa_daily` 都是大重构 | 962 个单测 + pyright 也守得住，只是漏改要跑测试才发现 |
| 成熟的 HTTP / TLS 库 | 能 | 7 条 HTTP/TLS fix 里约 3 条用 hyper / rustls / rcgen 不会出 | 根因是只用标准库；守护进程这层再出协议问题时，单独评估只换这一层 |
| 和 maa-cli、MaaCore 同语言 | 能 | 能直接拿结构化回调（§5） | 给 maa-cli 打小补丁就能拿到，我们这边仍是 Python |

### 生产使用

| 优势 | 能否体现 | 依据 | Python 内的替代 |
|---|---|---|---|
| 单一二进制，不依赖解释器 | **能，最实在的一条** | 守护进程 plist 写死 `~/.local/bin/python3`，它链到 uv 的 `cpython-3.12.13`；launcher 部分就是为解释器 ad-hoc 签名、TCC 授权、防火墙按版本路径放行而存在；历史上 2 条解释器问题；Mac App 的 `autoPython` 会挑到 Hermes venv（已知） | M1a 修 `autoPython`，Mac App 和 plist 用同一个固定解释器路径；升级 Python 当成一次部署 |
| 性能、内存 | 不能 | §2.4 | 不需要 |
| 并发安全 | 基本不能 | 并发问题在进程之间和文件上，不在线程里 | 锁内重读 + 只合并（Review 的修法） |
| 没有未捕获异常 | 不明显 | Rust 也会 panic；守护进程已逐字段容错（`0436df5`） | — |

## 4. Python 在本项目的优势与劣势

### 优势

开发维护：
- **现状零成本**：2.7 万行代码、2.1 万行测试、67 条不变量、31 份事故记录，都是围着现有实现写的。
- **测试好写**：`mock.patch` 随手替掉时钟、子进程、网络；Rust 要先设计 trait 才能注入，测试等于重新设计。
- **迭代快**：主要改动来源是游戏那边（新活动、新主页、新弹窗），常常当天改当天部署。不用编译，单测约 6 秒。
- **零第三方依赖**：没有供应链风险；Rust 版估计要上百个 crate（tokio、hyper、rustls、serde、chrono-tz、reqwest 等及其间接依赖）。
- **胶水代码短**：大量调外部命令、解析文本和 JSON，Python 写这些最省事。

生产使用：
- **线上直接看源码排障**：`~/.wados-maa/scripts/` 就是源码，报错带文件和行号；Rust 线上只有二进制，要先对上是哪个提交编出来的。
- **部署和回滚简单**：拷文件，`deploy.py` 自带备份；Rust 要编译、签名，还要确认 TCC 授权跟着走。

### 劣势

- 解释器会漂移（§3 生产第一条）。
- 标准库 HTTP / TLS 要自己补协议细节。
- 大重构时漏改靠测试发现，不是编译时发现。
- 要兼顾多个 Python 版本：CI 跑 3.11 / 3.12，曾被系统 Python 3.9 坑过一次（`405dc47`）。

## 5. maa-cli 与 MaaCore 直连

### 5.1 上游现状（11-26 查）

- 本机 maa-cli `v0.7.8`（brew，`maaassistantarknights/tap`），MaaCore `v6.23.2`，Beta 通道；库在 `~/Library/Application Support/com.loong.maa/lib/`。
- 上游是 13 个 crate 的工作区，`maa-sys`（FFI）、`maa-core`（安全封装：`Assistant`、`Callback`）可以单独用。两者**都没发布到 crates.io**，只能 git 依赖钉 tag。
- 许可证 **AGPL-3.0-only**。fork 它或链接 `maa-core`，我们的那部分代码都要按 AGPL 发；`maa-remote/` 现在是 MIT（`gui/` 已经是 AGPL）。
- maa-cli 在 MaaCore 之上做的事：资源加载顺序、TOML 任务配置和条件转成任务参数、PlayCover 连接、信号停止、掉线重连、安装和更新。这几块源码约 300KB（`config/asst.rs`、`config/task/*`、`config/import.rs`、`run/preset/copilot.rs`、`run/callback/*`）。

### 5.2 现在的数据链路是有损往返

MaaCore 发 JSON 回调 → maa-cli 翻成英文文本 → 我们用正则抠回来。解析点：

- `maa_daily.py:726` `Mission started (N times …)`、`:737` `Use N expiring medicine`、`:781` `Drops:`、`:884` 任务 Start / Completed / Error / Stopped；
- `maa_copilot_worker.py:480` `CurrentSteps Deploy`、`:492` `Copilot Error`、`:778-779`、`:1738` `[标签] Completed`；
- `maa_clearing.py:411` 只有 `-vvv` 才有的 `UnknownSubTaskExtraInfo`。

战报和实际不一致那一类问题（G4、X7、X8）的根子在这里。

MaaCore 自己的 `debug/asst.log` 记着每条回调的完整 JSON（`Assistant::append_callback | SubTaskExtraInfo {"class":"asst::StageDropsTaskPlugin", …}`），11-21 以来的真实场次都在。它是内部日志、64MB 轮转、全局共用，只适合做对照，不能当线上契约。

### 5.3 三种做法

| | 做法 | 代价 | 收益 |
|---|---|---|---|
| **L1** | 给 maa-cli 打几十行补丁，加 `--callback-jsonl <路径>` 原样写出每条回调；Python 解析改读 JSON | 3～5 天，可并进 M1a 结构化战报 v2；maa-cli 改为自编译、不再走 brew，07:50 上游更新流程要跟着改。补丁若被上游接受可回到 brew | 结构化战报的根基 |
| **L2** | 自写 Rust runner 链接 `maa-core`，替换 `maa run` / `maa copilot` | 重写或 fork 复用 §5.1 那 300KB，2～3 周 + 真机 | 同 L1，外加执行过程完全可控 |
| **L3** | 整个后端搬进 maa-cli 的 fork | 5～8 周 + 长期维护 fork | 单一 Rust 程序 |

**对「fork maa-cli 再加回现有实现」的看法**：底层方向对，最难的 MaaCore 接入层不用自己写；但我们 2.7 万行几乎都在 maa-cli 之上（调度、计划、材料、抄作业托管、森空岛、守护进程与 API、Bark、续签、窗口与台前调度、游戏退出看门狗、恢复梯子），fork 省不掉这部分，5～8 周基本不变。而且 maa-cli 很活跃、MaaCore 跟 Beta 每天更新，整个后端搬进 fork 会回到 MaaMacGui「改太多、合不动上游」的局面（11-09 刚为此停止合并上游）。

### 5.4 Spike 方案（备用，未开工）

如果以后要做 L1 或 L2，先跑这个 Spike：

| 步 | 碰游戏 | 时长 | 内容 |
|---|---|---|---|
| A 离线对照 | 否 | 半天 | 用 `asst.log` 里真实场次的回调 JSON，逐个对照 §5.2 的解析点，分成「JSON 里有 / 只有 maa-cli 自己算 / 都没有」 |
| B 编译 | 否 | 半天 | 装 Rust（maa-cli 要求 1.88+、edition 2024）；仓库外编 maa-cli `v0.7.8`，用我们的 `daily.toml` 对比和 brew 版 `--dry-run -vv` 的任务参数；加 JSONL 补丁；另写约 100 行小程序经 `maa-core` 加载本机 MaaCore 和资源 |
| C 真机 | 是 | 约 1 小时 | 持 `run.lock`，用 `maa_playcover` 开游戏、摆窗；补丁版 maa-cli 跑只回主界面的 StartUp 拿 JSONL；小程序连 `127.0.0.1:1717` 截图、跑同一个 StartUp |

C 步约束：不刷理智、不领奖、不碰商店；离早晚场 30 分钟以上；游戏在跑就放弃；不部署、不动守护进程、不发 Bark。A 步单独做也有价值：能回答「回调够不够用」。

## 6. 建议

1. **解释器**：M1a 修 `autoPython`，Mac App 和 plist 统一用一个固定解释器路径（已在 ROADMAP）。
2. **类型**：M1a 契约护栏里对状态文件和回执模块开 pyright strict，加跨端 golden fixture。
3. **HTTP / TLS**：先不动；守护进程这层再出协议问题时，单独评估只换这一层。
4. **结构化回调**：做结构化战报 v2 时考虑 L1，先做 §5.4 的 A 步确认回调覆盖面。
