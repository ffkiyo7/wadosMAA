# 全仓评审（2026-11-09，北京时间）

> 范围：架构与产品设计、功能链路与实现、GUI 的 UX。基于 `dev` @ `49d742b`。
> 只读代码和文档，没改任何代码。maa-remote 777 个单测本机全过。
> GUI 没能截图验证：本想在开发副本里模拟「运行中」截图，截图授权没给，所以 §3.1 的布局问题是按代码和尺寸推算的。开发副本已还原。

## 一句话结论

功能已经很全，单测和不变量也很扎实；但**执行引擎靠「跑完一整条链再解析文本日志」来判断发生了什么**，每遇到一种新的失败方式就要加一个专门的识别函数、一条重试分支、一组配置项和一条不变量，所以总在打补丁。GUI 的问题主要有三个：**文案**（锁、派发、上游、cron、MaaCore 这类实现层的词直接摆在用户面前，见 §3.5）、**信息架构**（按代码模块分组，不是按用户要做的事分组）和**运行中的反馈**（不知道进度，也看不到重试）。

## 0. 为什么总在打补丁

### 现象

- 最近 5 天 5 个 `fix`，全在设备层和恢复逻辑：三丽鸥主题、虚拟屏开窗、台前调度缩略图（两次）、游戏没登录上。
- 最近两次修复各加了 500～740 行（`49d742b` 给 `maa_daily.py` 加了 307 行）。`maa_daily.py` 有 2440 行，`execute()` 一个函数约 400 行。
- 恢复逻辑散在三层，各管各的：
  - `run_maa()`：跑的过程中摆窗、代理失误熔断；
  - `run_maa_resilient()`：连接失败重开、没登录上重启；
  - `execute()`：熔断后补跑、主关空跑改刷后备关。
- 每类失败都有自己的次数、等待、预算和「放弃」标记，函数之间**靠字符串传信号**：`execute()` 用 `CONNECT_GAVE_UP in line` 在自己写的日志里找关键词，以此决定要不要补跑（`maa_daily.py:2254`）。
- 不变量已经 61 条，DEV_GUIDE 有 2051 行，其中一大半是事故经过。

### 根因

1. **事后解析文本日志**：`maa run daily` 一条链跑到底，结束后才能根据输出判断成败。MaaCore 还会「假完成」：没登录上时 Mall / Award 也报 Completed；`AllTasksCompleted` 骗过了重开闸门；代理失误时返还的理智被算成掉落。所以每种新失败都要再写一个识别函数。
2. **环境本身不稳**：台前调度 + BetterDisplay 虚拟屏 + PlayCover 恢复窗口。最近 3 次事故有 2 次是台前调度把游戏收进了侧边栏。
3. **恢复策略按事故逐条往上加**，没有统一的模型。
4. **真机没法按需复现**，只能上线后等下一次事故来验证。

### 建议（大胆版）

| # | 建议 | 效果 |
|---|---|---|
| A | **把一条长链拆成「逐个环节跑 + 环节之间体检」**。StartUp 单独跑，用已有的 `verify_home_screenshot()` 确认回到主页后，再逐个跑剿灭、刷理智、基建、公招、商店、领奖。每跑完一段，检查一次窗口在屏、截图不是空的、画面在主页 | 失败能定位到具体环节；只重跑失败的那段，补跑和后备关这两套特例就不需要了；后面的任务不会再被前面的「假 Completed」带偏；GUI 能拿到确定的进度。代价是每段多几秒 Core 初始化 |
| B | **统一失败分类和恢复梯子**：`classify(证据) → Failure(kind, 能否重试, 是否需要重启)`，恢复步骤按一张表走（摆窗 → 切走再切回 → 重启 → 等一会儿再重启），共用一份预算。字符串标记改成类型化的 `RunOutcome` | 以后遇到新事故，只需加一条分类规则和一个回放用例，不用改控制流 |
| C | **把认画面做成一等能力**：已有 `ocrbox` 和 `HOME_MARKERS`，扩成 `screen_state()`，返回无窗口 / 缩略图 / 空白 / 主页 / 登录报错 / 结算页 / 未知。开跑前、两段之间、出错时都调一次 | 日志认不出的情况可以靠画面兜底 |
| D | **事故回放和演练**：每次事故的真实日志和截图放进 `tests/fixtures/incidents/<日期>/`，用一张表驱动测试。再加 `maa_daily.py rehearse <fixture>`：用假的 `maa` 回放日志，完整走一遍 `execute()`（Discord 用桩），部署前跑 | 部署前就能发现链路问题 |
| E | **从环境上解决**：跑场期间不开台前调度，或者本机干脆关掉 | 比 winmove、切走再切回、重启这三级救援可靠（**需要你决定**） |
| F | **可靠性统计**：每场把重试、重启、摆窗次数、失败分类、耗时追加进 `runs/index.jsonl`，GUI 显示近 30 场成功率 | 补丁有没有用，一眼就能看出来 |

## 1. 架构

### 1.1 Discord 是日常执行的硬依赖（P0）

- `maa_daily.py:2031-2034`：没有 `channel_id` 直接抛异常；`discord_token()` 读不到 `.env` 也抛。
- 开跑消息、建子区都放在主流程的 `try` 里（`maa_daily.py:2176-2216`）。`discord_request` 有 4 次重试，但只要 Discord 连不上超过几秒、或者 token 失效，**整场判失败并关掉游戏**，一关都没打。
- HANDOFF 遗留的第 5 条（开发副本里 `run local` 起不来）也是这个原因。
- **建议**：通知改成可以插拔的出口（Discord / 本机通知 / 只写文件）。发送失败只记一条日志，执行引擎不依赖任何通知通道。

### 1.2 `last_run.json` 同时被多方写，内容混杂

- 会写它的有日常、抄作业、Depot、上游更新。里面既有本场的 28 个字段（`RUN_SCOPED_LAST_RUN_KEYS`），也有跨场的状态（剿灭周进度、锁冲突、资源更新结果、`threads`）。
- 「最近几场」因此只能显示一场。HANDOFF 第 3 条里读到旧字段的问题，也是这个结构造成的。
- **建议**拆成三类文件：
  - `runs/<id>.json`：每场一份，跑完不再改；
  - `runs/index.jsonl`：只追加，GUI 的「最近几场」和成功率直接读它；
  - `state.json`：跨场状态。

### 1.3 进度：Python 已经算过一遍，Swift 又解析一遍

- `run_maa()` 每 5 秒算一次 `progress_content()` 去更新 Discord（`maa_daily.py:1396`）。
- GUI 的 `RunStageParser.swift` 又读同一份日志，还只能按「第一个 Fight 就是剿灭」来猜；重试、重启、补跑、后备关它都看不到。
- **建议**：maa-remote 在同一个 5 秒循环里顺手写一份 `runs/<id>.progress.json`：
  - `steps[]`：每个环节的 key、label、state、开始和结束时间；
  - `current`：正在跑的环节；
  - `fight`：已打次数、预计次数、理智、掉落；
  - `notes[]`：重试和重启记录；
  - `eta`：预计结束时间。

  GUI 只负责渲染，可以删掉 `RunStageParser`。这是 §12 接口的变更，两边在同一个提交里改。

### 1.4 两套 MaaCore 运行时（大胆建议：GUI 不再 fork 上游）

- 现状：
  - GUI 进程直接链接 maa-cli 的 dylib（弱链接 + rpath + `disable-library-validation`），maa-cli 一更新就要重启 App（`RemoteGate.coreMismatch`）；
  - 还要持续合并上游 MaaMacGui（AGPL，上游正在重构 ViewModel）。
- 真正要用 GUI 自带 Core 的，只有偶尔才用的肉鸽、生息演算、手贴作业和实用工具。
- 本机 maa-cli 已经有 `roguelike`、`reclamation`、`copilot`、`ssscopilot`、`paradoxcopilot` 这些子命令。
- **建议先做一次 spike**：确认这些子命令能覆盖你实际在用的功能，能覆盖的就让 GUI 退成纯粹的 maa-remote 前端。
  - 好处：不再链接 Core、不再合并上游；资源加载、更新和锁不再是两套。GUI 的有效代码只剩 `Remote/` 约 5400 行。
  - 代价：上游的实用工具页（公招识别、仓库识别等）要么砍掉，要么改走 maa-cli。

### 1.5 调度：Hermes cron + UTC + 打补丁

- deploy.py 要给 Hermes 打 4 处补丁，Hermes 每次升级都得重打（§11.2）。还出过 config.yaml 写坏、全部 cron 提前 8 小时的事故（§11.17、§11.17b）。
- `maa_schedule.py` 要靠 `hermes cron edit/pause/resume` 跟配置对齐。
- **建议**：调度改用本仓库自己管理的 launchd（`StartCalendarInterval`，按本地时间写，不用换算 UTC），GUI 直接读写。Hermes 只负责 Discord 按钮和聊天。中期再看能不能把「给 adapter 打补丁」换成 Hermes 的插件接口，或者自己写一个独立的小 bot。

### 1.6 其他结构问题（不急）

- `maa_action.py` 有 2012 行，Discord 入口、GUI 入口和闸门实现都在里面。可以按领域拆到 `commands/`，闸门单独放进 `gates.py`，两个 `dispatch` 只做路由。
- 文档太重：新会话每次修复都要先读完 2000 行上下文，这也是补丁越来越大的原因之一。建议把 §0.5、§11 的事故经过挪到 `docs/incidents/`，DEV_GUIDE 只写现行机制，不变量按模块分组。

## 3. GUI 的 UX

### 3.1 运行状态条（你提到的两个问题）

**展开日志后显示不对**（按代码推算，没截图）：

- `RunStateView` 放在详情栏工具栏的 `.navigation` 位置，加了 `.fixedSize()`，一整行依次是：圆点、「运行中」、「日常·手动（自 17:59）」、阶段名、140pt 的进度条、「停止」按钮。
- 宽度算一下：窗口最小 900，边栏理想宽度 212，日志检查器理想宽度 300，详情栏只剩约 390pt；而这一行本身就超过 400pt。放不下时，macOS 会把它挤进溢出菜单或者截断。macOS 26 还会给每个工具栏项套一层玻璃胶囊，进度条在胶囊里也容易变形。

**进度条没有实际进度**：`Shell.swift:228` 用的是不定进度的 `ProgressView()`，只能表示「在动」。

**建议**：

1. 工具栏只留一个紧凑的胶囊，例如「● 刷理智 3/≈7 · 约 08:12 结束」，点开用 popover 看详情。
2. 打开日志时，检查器顶部固定一张「本场」卡片，上面是环节步骤条：

   ```
   ✅ 开始唤醒  ✅ 剿灭  ⏳ 刷理智 3/≈7  ○ 基建  ○ 公招  ○ 商店  ○ 领奖
   ```

   下面才是日志。
3. 进度怎么算：
   - 整体按计划里的环节数分段，这部分是确定的；
   - 刷理智这一段，用「已打次数 /（开场理智 ÷ apCost）」估算；
   - ETA 按历史上每个环节的平均耗时推算。

   数据来自 1.3 的 `progress.json`。在协议做好之前，可以先用现有的 `RunStageParser` 加上 `plan.tasks` 把步骤条做出来。
4. 重试、重启、摆窗要显示出来，例如「游戏没登录上，2 分钟后重启（1/2）」。现在 GUI 完全看不到这些，只能等战报。

### 3.2 日志检查器

- 现在是把 App 日志和阶段行按时间混在一起：maa-remote 写的说明（重试、摆窗）看不到，不能过滤，也没法直接打开本场的完整日志。
- **建议**：分成「本场」和「App」两段。「本场」显示进度事件，并提供「在 Finder 中显示本场日志 / 截图」。

### 3.3 设置与配置的信息架构（你提到的）

**现在配置散在 5 个地方**：

1. 日程与默认；
2. 日常配置（日常 / 高级，高级里又分自动定关、抄作业、森空岛、运行环境）；
3. 设置页（外观、maa-remote 环境、连接与游戏的 3 个弹出页、帮助）；
4. ⌘, 打开的上游设置窗口；
5. 首页「这一场」的临时覆盖。

**分组是按代码模块来的，不是按用户要做的事**。例如：

- `manual_run_blackout_minutes`（定时场前多久不接手动场）放在「抄作业」组；
- 熔断的 `proxy_failure_limit` / `salvage` 放在「日常」组；
- 「运行环境」11 项几乎全是超时秒数；
- 「开发 / 线上」、HERMES_HOME、Python 放在普通设置里；
- 几乎所有说明都写在 `.help()` 悬停提示里（首页 12 处、设置页 11 处），不把鼠标停上去就看不到。这是「指引不清晰」的直接原因。

**建议的新结构**（按一场日常从头到尾的顺序排）：

| 入口 | 放什么 |
|---|---|
| 今天 | 两场的计划（关卡、跳过、环节，可以改）、手动开一场、运行进度、最近几场 |
| 日常 | 时间表（早场、晚场的时间和开关）→ 每场做哪些环节 → 刷什么（默认关或自动定关，附「为什么选这关」）→ 剿灭、公招、信用商店、领奖的细项 |
| 抄作业 | 页面本身；右上角「规则」里放自动抄作业开关、每天尝试几次、重试间隔、离定时场多久不开新的一关 |
| 设置 | 外观、通知、账号（森空岛登录状态和过期提醒）、游戏与设备（虚拟屏名称、MaaTools） |
| 设置 › 高级 | 超时、重试、熔断、日志保留天数、cron 原文、环境、HERMES_HOME、Python。默认折叠，标注「一般不用动」 |

还有几条细的：

- 三个「定时场前 N 分钟」（`copilot_blackout_minutes`、`manual_run_blackout_minutes`、`auto_copilot_min_lead_minutes`）合并成一个「定时场保护时间」，其余在内部按它推算。
- 自动定关的 7 个数值参数：GUI 只给「自动定关 开 / 关」，加一个三档预设「省理智 / 补缺口 / 均衡」；原始数值和 JSON 编辑框放进高级。
- 说明文字不写长段（符合 AGENTS.md 的原则），但关键项下面放一行灰字，直接显示设置的效果，例如「早场 08:00 → 07:30 之后不接手动场」。这行字由数值算出来，不用悬停。
- ⌘, 的上游设置窗口和设置页重复，删掉或者改成打开设置页。
- 「连接设置」里的 MaaTools 地址和 maa-cli profile 是两份配置：GUI 里改了，maa-remote 不知道。要么只读显示 maa-cli 的那份，要么去掉这一项。

### 3.4 其他 UX

- **只有深色**：`.preferredColorScheme(.dark)`（`Shell.swift:124`），颜色写死成 hex。这和 K9「浅色、深色各设一张背景图」是矛盾的。
- **字号写死**：11.5 用了 17 次、11 用了 7 次，正文偏小，也不跟随系统字号。建议在 Theme 里定义 4 级语义字号，全部替换。
- **确认框是自己画的遮罩**（`Theme.swift:218`）：弹出时工具栏还能点，VoiceOver 也不会把它当成模态框。建议改用 `.sheet` 或 `.confirmationDialog`。
- **战报横幅信息不够**：成功时只挑「刷理智」那一行。建议改成战报卡，显示各环节的 ✅ / ❌、掉落、截图缩略图，再加一个「打开 Discord 子区」。
- **「游戏锁 空闲 / 使用中」的大字卡信息量低**，和状态条重复。建议把这个位置让给「今天两场的计划」。
- **边栏「自动抄作业」的角标是未通关的关数**，活动期间会一直挂着一个数字，成了噪音。建议只在有「能打、练度也满足」的关时才显示。

### 3.5 文案：界面上只能出现玩家听得懂的词

**问题**：界面上的字大多是**写代码时的说法**，没有翻译成用户的话。GUI 里 Swift 写的字，加上 maa-remote 回执里被 GUI 原样显示的字，逐条过了一遍，主要有这几类：

**原则**（建议写进 AGENTS.md 的「页面设计」一节）：

1. **只用两种词**：游戏里的词（理智、关卡、剿灭、基建、公招、作业、练度、助战、碎石），玩家都懂；再就是日常用语。实现层的词一律不出现：锁、派发、闸门、上游、cron、Hermes、maa-remote、maa-cli、MaaCore、MaaResource、MaaTools、进程、token、回执、退出码、schema、不变量编号、文档编号。
2. **说结果和下一步，不说机制**。「被挡住」不算一句话，要说清「为什么现在不行，什么时候能行，我能做什么」。
3. **一个概念只用一个词**，全 App 和 Discord 战报统一（见下面的词表）。
4. **报错分两层**：界面上只写一句人话，技术细节收进「详情」或「复制诊断信息」，留给排障时用。
5. **开发者用的东西不进普通设置**：环境、HERMES_HOME、Python、cron 原文、版本号细节，都放进默认隐藏的「开发者」区（例如按住 ⌥ 才显示）。

**落地方法**：

- **maa-remote 回执拆成三段**：`code`（给程序判断，例如 `blocked.session_soon`）、`message`（给人看的一句话）、`detail`（技术细节）。GUI 按 `code` 显示自己的文案，`detail` 只放进「详情」。这样以后改 Discord 的措辞也不会影响 GUI。这是 §12 接口的变更，两边一起改。
- **设置项的标签放回 maa-remote 的 `FIELDS`**，GUI 照常读。按上面的词表把 label 和 help 全部重写一遍。高级里的算法参数换成预设档位（§3.3）。
- **加一条守门测试**：建一份禁用词表（锁、派发、cron、HERMES、MaaCore、maa-cli、上游、token、进程、不变量、PLAN_、schema 等），扫 Swift 里所有 `Text` / `Label` / `Button` / `.help` 的字符串，以及 `dispatch_gui` 回执里的 `message`。命中就红，开发者区加白名单。这和 maa-remote 用测试守不变量是一个思路，改完不会慢慢退回去。
- **Discord 的战报和卡片**也是给人看的，同一份词表一起用。
